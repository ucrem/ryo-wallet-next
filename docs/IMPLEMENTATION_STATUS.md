# Implementation status

Updated 2026-10-05 for next-release hardening on the 0.1.0-alpha.6 baseline. This branch includes wallet operations, native import, scan persistence and saved-wallet reopening. Current-fork funded tests await the Ryo developers' testnet restoration; platform production gates remain **in progress**. No stable release is declared.

## Implemented

- About exports a Rust-owned, allowlisted diagnostic JSON report without wallet secrets, identifying wallet data, paths, endpoints or raw logs. Schema 3 collects detailed OS version, memory and selected local storage facts on Windows, macOS and Linux, alongside WebView/runtime verification, build identity, uptime, selected preferences and node probe timing. Platform-specific memory/space source labels distinguish estimates and quota semantics; Unix ACL support remains unknown. Native collectors run in the Linux/macOS host CI jobs. The app/version, updates and diagnostics panels share one compact desktop row. Export cancellation and no-overwrite behavior are covered. See [Diagnostics](DIAGNOSTICS.md).
- Saved-wallet names are recovered from authenticated encrypted `next.name` during unlock and cached separately for the locked Home picker. Missing metadata cannot reconstruct a previously encrypted name until that wallet is unlocked once. The picker refreshes after unlock and rename. This cache is a display label, not wallet authority.

- Recovery sync now tracks processed blocks through private wallet RPC stdout while the single-threaded upstream refresh is busy. Background reads have bounded deadlines and retry automatically; balances/history retain explicitly labelled previous snapshots. Node probes retain recent heights with a delayed-response label, without claiming reachability/readiness. See [Wallet synchronization](WALLET_SYNC.md) for evidence and remaining full-chain gates.
- Settings exposes General and Preferences in the top menu. General covers local/remote/bootstrap mode, a native folder picker, bounded daemon options and isolated network selection. Global preferences cover light/dark/system themes, native tray/startup behavior, advisory form warnings and Rust-owned generation-checked inactivity locking. General changes require stopped wallet/node processes; preferences can save during sync. See [Settings behavior and validation](SETTINGS.md).
- Home stacks the three wallet choices in the original one-third-width column, with the existing Ryo vector symbol on the right fading from left to right.
- The compact top menu exposes Wallet, Receive, Send, Address Book and TX History. Receive covers labels, per-address balances, QR codes and native SVG exports; payment requests round-trip exact RYO amounts. Contacts and the wallet name persist through wallet attributes; transaction notes use the upstream notes API.
- Wallet pages reset on tab/session changes: Wallet actions, its open menu and previous forms are discarded immediately; returning does not restore them. The balance visibility preference remains shared across wallet tabs.
- Receive, Send and Address Book use a compact single-row wallet summary and denser forms. The Receive selector lists labels/indexes/used status, with the full selected address shown only next to its QR. Address selection updates QR/label and resets payment request fields. Long address/contact lists scroll within their panels.
- Rust prepares transfer/sweep drafts with `do_not_relay=true` and `get_tx_metadata=true`, retaining signed metadata in zeroizing memory. The UI receives only the exact address, amount, fee, hashes and a five-minute token. Confirmation consumes the token once and relays the same metadata. Cancel, expiry, lock and session changes invalidate drafts. The journal writes each hash as unknown before relay, survives restart, and blocks preparations while a previous outcome remains uncertain. Reconciliation does not retransmit.
- Wallet actions include rename, password change, password-protected private phrase/view/spend-key display, full/spent rescan and native key image import/export. Secrets use local component state, never read-query caches, and hide after one minute. The runtime has no password-verification RPC, so reauthentication rewrites to the same password. Removal requires password, DELETE and backup confirmation, then locks and archives the encrypted wallet under `removed-wallets`.

- The wallet flow verifies the reviewed 0.6.1.0 wallet RPC digest before use, creates a fresh app-owned wallet, presents its mnemonic for paper backup, checks three hidden words, records backup acknowledgement privately, locks the process, and reopens by password. An interrupted backup remains pending and can be resumed after password unlock. The already published alpha.4 installers omit the runtime; new supported-target packaging includes it but has not been promoted.
- After backup acknowledgement, an open long-address wallet can create account-0 receive subaddresses. Rust saves each new address through wallet RPC before returning it; the dashboard lists saved addresses and copies the selected one. A disposable test confirms persistence after reopening and deterministic regeneration from the same recovery phrase.

- Two-member Cargo workspace: reusable `ryo-wallet-service` and a minimal Tauri 2 host.
- Rust domain amount parsing with exact nine-digit precision, checked `u64` arithmetic, network enum and string-based IPC amount DTOs generated to TypeScript by `ts-rs`.
- Typed node configuration distinguishes an app-managed loopback node from an explicitly selected remote host. It rejects URLs, paths, credentials and invalid ports. `NodeService` owns a verified bundled local `ryod` independently of wallet RPC, with isolated blockchain storage and allocated ports. Explicit Start/Stop controls and node status remain available while the wallet is locked. Wallet lock stops only wallet RPC; app exit and update installation stop both owned processes.
- Private, network-isolated storage and opaque IDs are implemented. Unix directories use mode 0700. Windows app-owned subdirectories use protected current-user/LocalSystem DACLs, with inherited protection for new files and explicit protection for imported/existing wallet pairs. Existing user-owned Modify-only storage is secured through a same-handle DACL-only fallback without requesting an unnecessary ownership change; other owners/reparse points remain excluded from that fallback. A disposable reviewed-RPC fixture verifies authenticated startup without opening a wallet. Startup feedback distinguishes storage, launch, credentials, network transport and readiness failures without raw private errors. Selected parent folders and imported originals retain their permissions. Full installed-platform acceptance remains open.
- Existing wallet import is connected to the desktop Open wallet screen through a scoped Rust-owned native file picker. File selection and pair validation precede display of the filename, existing-password entry and original-file backup acknowledgement. An opaque native selection token is bound to the current data folder/network. Import then copies the wallet and matching `.keys` into a fresh app-owned directory; only the copy is opened. Cancelled selection imports nothing and requests no password. The copy rejects relative paths, `.keys` selection, symlinks and oversized files, and reports incorrect passwords or unsupported multiple-account/multisig scope. Failed opens stop their RPC process before deleting only the fresh copy. A disposable Windows test with the reviewed RPC verifies cached name/subaddresses, short-password opening, incorrect-password cleanup, reopening and byte-for-byte unchanged originals. Windows ACL protection is now implemented; funded legacy-cache and clean installed compatibility remain open gates. See [Wallet import](WALLET_IMPORT.md).
- Sidecar verification requires an absolute regular file with an exact reviewed SHA-256 digest before launch. The Linux 0.6.1.0 wallet RPC release has been exercised locally with disposable wallets. A shared runtime manifest now records verified archive and executable hashes for Linux x64, macOS Intel and Windows x64; no native upstream Apple Silicon binary is available.
- The process supervisor accepts verified binaries, structured arguments, private absolute working directories and deadline-bound stop fallback. Wallet stdin is closed; daemon stdin accepts only its fixed shutdown command. Windows inherits only `SystemRoot`, hides sidecar consoles and attaches each child to a kill-on-close Job Object. Abrupt-owner-exit termination is tested; a small spawn-to-assignment window remains. Unix process-group ownership and installed crash recovery remain open gates.
- Generated RPC credentials are read from a fixed runtime filename with absolute-path, regular-file and bounded-size checks. Unix mode and Windows owner/DACL checks use the same open handle as the read. Broad/null Windows ACLs and final reparse points are rejected. Credentials remain Rust-only with redacted debug output.
- Wallet-RPC launch arguments are now built as structured values: explicit `127.0.0.1` binding, network flag, app-owned wallet directory, selected daemon address, and private working directory. They never include `--disable-rpc-login`, a wallet password, or RPC credentials.
- `WalletRpcSession` joins verified launch, generated-login polling, authenticated `get_languages` readiness, and exit-confirmed shutdown with a bounded force-stop fallback. Its Linux path passes opt-in tests with the reviewed release.
- A single-owner async `WalletService` serializes startup, import opening, creation, restoration and lock operations, preventing overlapping lifecycle transitions or locks held across RPC awaits. The creation UI records backup acknowledgement after a three-word check.
- Create and restore are now queued through the same service actor and allocate a fresh app-owned wallet directory before their RPC call. Creation immediately retrieves only the mnemonic into a one-time non-serializable result for the dedicated backup flow; it is not stored by the actor. Any uncertain creation or restoration faults the session and preserves artifacts for recovery instead of silently retrying.
- Narrowly scoped Tauri commands expose the service lifecycle, wallet creation, backup confirmation, saved receive addresses and an exact balance snapshot. Their permissions are explicit; there is no generic wallet-RPC bridge.
- The service provides a typed, read-only `WalletOverview` for an open wallet: primary address and exact total/unlocked/locked atomic amounts are returned as non-floating strings, with the session generation for stale-response rejection. The UI formats balances in RYO without converting them through floating-point numbers.
- Non-secret node, theme and idle-lock settings now validate before persistence and are written through a private temporary file before rename. Wallet passwords, seeds, RPC credentials and wallet paths are deliberately absent from the settings schema.
- First-run storage selection is now a Rust-owned native folder picker. It canonicalizes the chosen directory, creates the private network/wallet/runtime directories before accepting it, and persists the selection atomically in the native app configuration. The WebView cannot submit a path; it receives the selected path only to display the user’s current configuration.
- Read-only, typed Rust wallet RPC calls: `get_languages`, `get_height`, `get_balance`, `get_address`, and `parse_uri` address validation. A local daemon `get_info` health adapter is also present. These return domain data or redacted typed errors, not raw JSON-RPC objects.
- Typed wallet-RPC calls cover opening an app-owned wallet, closing it, and requesting an orderly wallet-RPC shutdown. Passwords use zeroizing Rust storage and wallet filenames are derived from opaque internal IDs; the WebView has narrow create/open/lock commands but no generic RPC bridge.
- After creation, restoration, or import opening, the service probes the source-defined `get_accounts` and `is_multisig` methods and closes/rejects any multi-account or multisig wallet before it becomes usable in the account-zero UI. Watch-only detection remains an explicit compatibility gate because the client deliberately does not request private keys merely to classify a wallet.
- Typed internal creation and seed-restoration calls default new wallets to long addresses and bind all output to an app-owned wallet ID. The desktop restoration form now passes a normalized phrase, new password and optional scan start height through a scoped Tauri command. A successful restore enters the existing three-word backup check before receive-address actions become available. Packaged restoration has not yet been exercised on this host.
- The creation client exposes `query_key(mnemonic)` through a non-cloneable, non-serializable recovery-phrase type. The creation UI clears the displayed phrase after confirmation or lock. The separate Wallet actions API retrieves phrase/view/spend keys only after password reauthentication and returns the dedicated zeroizing secret response described above.
- A tested lifecycle state machine makes sidecar readiness, wallet opening, locking, fault recovery, and session-generation changes explicit. The reviewed Linux sidecar passes disposable create, lock, restart and reopen tests.
- Digest-authenticated loopback HTTP transport with fixed address, no proxy/redirects, bounded timeout and response size, request ID checks, and zeroizing request/response buffers where owned by the service. The HTTP client and upstream C++ process may make their own copies; this implementation does not claim full memory erasure.
- React 19/Vite 8/Tailwind 4/shadcn onboarding scaffold exposes the real data-location state and opens a native picker through one scoped command. No generic shell/filesystem/HTTP permission is exposed to the WebView.
- The first onboarding screen uses Ryo's blue symbol from the upstream wallet's vector artwork, including a regenerated desktop icon; its provenance and independent-project status are documented in `ASSETS.md`.
- Onboarding uses a desktop shell with Wallet, Setup and About in the top menu and a second navigation row for setup steps. The user approved this layout; the original sidebar remains available in a separate comparison preview. An independent About screen displays the native executable version, prerelease status, and a locally bundled changelog; it does not depend on wallet setup state. The document itself does not scroll; the main area scrolls for longer content. The Tauri window has a 1400 × 800 minimum size.
- After selecting a wallet flow and data location, the UI offers Mainnet local or explicit remote node configuration. Rust constructs and validates the node choice before saving it to the private settings file; malformed existing settings are not silently overwritten. Data-location and node changes are refused while the wallet service is active. The UI explains the remote node's IP and scan-request visibility.
- Setup can continue with unchanged saved node settings while the node syncs or a wallet is open. This navigation performs no save or node restart. Opening Setup directly also initializes the default open-wallet flow when continuing, so the summary and wallet screens remain usable.
- The main top menu is 48 px high; the 32 px setup navigation appears only in setup screens. Main content spans the available width, and wallet entry forms use two columns on desktop. A 40 px single-line footer shows node and wallet heights, percentages and inline progress indicators. A reachable node still syncing no longer reports wallet status as "Node connecting".
- Development uses a separate CSP for Vite's injected scripts, styles and hot-reload connection. On Linux hosts with the NVIDIA driver, the desktop entry point disables WebKitGTK's problematic DMABUF renderer before constructing the window, while respecting an explicit environment override.
- Exact Cargo and pnpm lockfiles plus basic read-only GitHub Actions checks. Original project code uses the MIT license; the packages are marked `publish = false` to prevent accidental registry publication.

## Upstream compatibility finding

GitHub's latest core release is [0.6.1.0](https://github.com/ryo-currency/ryo-currency/releases/tag/0.6.1.0), published in 2020. Its source tag resolves to `166cf188bf351e3eecff904450eda2785f9d0357`. The 2026 inspected commit is `185dd1fa33ba88c88bb22df9069ad368c0f9a27e`. A Git diff found **no changes** between these commits in six RPC-relevant files: `wallet_rpc_server.cpp`, `wallet_rpc_server.h`, `wallet_rpc_server_commands_defs.h`, `wallet2.cpp`, `core_rpc_server.cpp`, and `core_rpc_server_commands_defs.h`. Registered methods and inspected wire shapes used by the current client therefore match at source level. The Linux 0.6.1.0 release archive was verified against its published SHA-256 and a valid signature from the upstream `mosu_forge` signing key (local trust is not asserted), then its wallet RPC binary was exercised only through disposable no-fund tests. In an isolated Fedora container, an out-of-tree source configuration required `-DCMAKE_POLICY_VERSION_MINIMUM=3.5` for CMake 4.3; after adding the missing build dependencies and a build-only `boost::asio::io_service` compatibility shim, compilation reached a second source-age incompatibility: `cryptonote_config.h` declares `boost::uuids::uuid` network IDs as `constexpr`, while Boost 1.90 no longer provides a constexpr constructor. The upstream clone remains unchanged. A supported historical dependency profile or an upstream-reviewed modernization is required before treating a source build as a runtime fixture.
