# Foundation implementation status

Updated 2026-09-23. This follows the architecture investigation. Phase 1 is **in progress**. No transaction operation is exposed by the app.

## Implemented

- Two-member Cargo workspace: reusable `ryo-wallet-service` and a minimal Tauri 2 host.
- Rust domain amount parsing with exact nine-digit precision, checked `u64` arithmetic, network enum and string-based IPC amount DTOs generated to TypeScript by `ts-rs`.
- Typed node configuration distinguishes an app-managed loopback node from an explicitly selected remote host. It rejects URLs, paths, credentials and invalid ports; remote network transport is not implemented yet.
- Private, network-isolated storage paths and opaque wallet IDs are implemented. On Unix, directory creation enforces owner-only permissions; Windows ACL enforcement remains a platform-specific implementation gate.
- Existing wallet imports can now copy a selected wallet plus its `.keys` companion into a fresh app-owned directory without changing the originals. The copy rejects relative paths, companion-file selection, symlinks, and oversized files; it still needs platform ACL work and real wallet-RPC validation.
- Sidecar verification requires an absolute regular file with an exact reviewed SHA-256 digest before launch. No Ryo executable has been launched in this development environment.
- The process supervisor accepts only verified binaries and starts them with structured arguments, a private absolute working directory, no inherited environment or stdio, and a deadline-bound force-stop fallback. Process-group and Windows Job Object handling remain platform-specific release gates.
- The generated wallet-RPC login file is read only from a fixed runtime filename, with an absolute-path, regular-file, size, and Unix owner-only-permission check. Its parsed credentials remain Rust-only and redact debug output; Windows ACL verification remains a release gate.
- Wallet-RPC launch arguments are now built as structured values: explicit `127.0.0.1` binding, network flag, app-owned wallet directory, selected daemon address, and private working directory. They never include `--disable-rpc-login`, a wallet password, or RPC credentials.
- `WalletRpcSession` now joins verified launch, generated-login polling, authenticated `get_languages` readiness, and exit-confirmed shutdown with a bounded force-stop fallback. Its successful real-runtime path remains unverified until a reviewed Ryo sidecar is available on this host.
- A single-owner async `WalletService` serializes startup, import opening, creation, restoration and lock operations, preventing overlapping lifecycle transitions or locks held across RPC awaits. Backup acknowledgement still needs a user-facing flow.
- Create and restore are now queued through the same service actor and allocate a fresh app-owned wallet directory before their RPC call. Creation immediately retrieves only the mnemonic into a one-time non-serializable result for the dedicated backup flow; it is not stored by the actor. Any uncertain creation or restoration faults the session and preserves artifacts for recovery instead of silently retrying.
- Narrowly scoped Tauri read commands expose the actual service lifecycle and, only while a wallet is open, its primary address plus exact balance snapshot. They have separate capabilities; no secret or wallet-mutating command is exposed to the WebView.
- The service provides a typed, read-only `WalletOverview` for an open wallet: primary address and exact total/unlocked/locked atomic amounts are returned as non-floating strings, with the session generation for stale-response rejection. It is not exposed to the WebView until the unlock/onboarding UI is ready.
- Non-secret node, theme and idle-lock settings now validate before persistence and are written through a private temporary file before rename. Wallet passwords, seeds, RPC credentials and wallet paths are deliberately absent from the settings schema.
- First-run storage selection is now a Rust-owned native folder picker. It canonicalizes the chosen directory, creates the private network/wallet/runtime directories before accepting it, and persists the selection atomically in the native app configuration. The WebView cannot submit a path; it receives the selected path only to display the user’s current configuration.
- Read-only, typed Rust wallet RPC calls: `get_languages`, `get_height`, `get_balance`, `get_address`, and `parse_uri` address validation. A local daemon `get_info` health adapter is also present. These return domain data or redacted typed errors, not raw JSON-RPC objects.
- Typed internal wallet-RPC calls now cover opening an app-owned imported wallet, closing it, and requesting an orderly wallet-RPC shutdown. Passwords use zeroizing Rust storage and wallet filenames are derived from opaque internal IDs; these calls are not exposed to the frontend yet.
- After creation, restoration, or import opening, the service probes the source-defined `get_accounts` and `is_multisig` methods and closes/rejects any multi-account or multisig wallet before it becomes usable in the account-zero UI. Watch-only detection remains an explicit compatibility gate because the client deliberately does not request private keys merely to classify a wallet.
- Typed internal creation and seed-restoration calls default new wallets to long addresses and bind all output to an app-owned wallet ID. The one-time backend handoff for backup recovery material is wired; its keyboard-accessible frontend acknowledgement and verification remain to be built, as does real sidecar validation.
- The wallet client now exposes only `query_key(mnemonic)` through a non-cloneable, non-serializable recovery-phrase type; it cannot request spend or view keys through this API. UI acknowledgement and lock-time clearing remain to be wired.
- A tested lifecycle state machine makes sidecar readiness, wallet opening, locking, fault recovery, and session-generation changes explicit. The service connects it to the process/RPC session, but no actual Ryo sidecar has been exercised.
- Digest-authenticated loopback HTTP transport with fixed address, no proxy/redirects, bounded timeout and response size, request ID checks, and zeroizing request/response buffers where owned by the service. The HTTP client and upstream C++ process may make their own copies; this implementation does not claim full memory erasure.
- React 19/Vite 8/Tailwind 4/shadcn onboarding scaffold exposes the real data-location state and opens a native picker through one scoped command. No generic shell/filesystem/HTTP permission is exposed to the WebView.
- The first onboarding screen uses Ryo's blue symbol from the upstream wallet's vector artwork, including a regenerated desktop icon; its provenance and independent-project status are documented in `ASSETS.md`.
- Onboarding now uses a desktop shell with a persistent left navigation menu and separate wallet-flow, data-location, node and summary screens. An independent About screen displays the native executable version, prerelease status, and a locally bundled changelog; it does not depend on wallet setup state. The document itself does not scroll; the main area scrolls for longer content. The Tauri window has a 960 × 720 minimum size.
- After selecting a wallet flow and data location, the UI now offers Mainnet local or explicit remote node configuration. Rust constructs and validates the node choice before saving it to the private settings file; malformed existing settings are not silently overwritten. Data-location and node changes are refused while the wallet service is active. The UI explains the remote node's IP and scan-request visibility and that this preview does not connect yet.
- Development uses a separate CSP for Vite's injected scripts, styles and hot-reload connection. On Linux hosts with the NVIDIA driver, the desktop entry point disables WebKitGTK's problematic DMABUF renderer before constructing the window, while respecting an explicit environment override.
- Exact Cargo and pnpm lockfiles plus basic read-only GitHub Actions checks. Original project code uses the MIT license; the packages are marked `publish = false` to prevent accidental registry publication.

## Verification performed here

- `cargo test -p ryo-wallet-service --locked`: 50 tests (40 library and 10 RPC transport integration tests), covering lifecycle transitions, storage/import safety, missing versus malformed settings, sidecar verification and shutdown, generated login-file validation, request wire shapes, amount boundaries, malformed responses, loopback restriction and disposable Digest challenge/response handling.
- Opt-in `real_wallet_rpc` tests verify the signed and SHA-256-checked Linux 0.6.1.0 release. One starts a loopback RPC process, reads its generated login, completes authenticated `get_languages`, creates a disposable long-address wallet, retrieves the mnemonic without logging it, then restores a second temporary wallet and verifies the primary address matches. Another drives create → one-time backup handoff → lock → fresh-process wrong-password rejection → correct reopen → lock → restore → lock through `WalletService`, including lifecycle state checks. A third creates an authentic source wallet, copies it through the import boundary and opens only the copied pair, verifying the source files are not changed and the primary address matches. They run only when `RYO_WALLET_RPC_BIN` identifies that reviewed binary; they contact no daemon and use no funds.
- `cargo fmt --all -- --check`: passed.
- `pnpm typecheck`, `pnpm lint`, `pnpm build`: passed using bundled Node 24.19.0 and pnpm 11.25.0. A frozen lockfile install also passed with pnpm 12.5.1. The repository pins Node 24.21.0 for CI; that exact Node patch was not available on this host.
- `pnpm test --passWithNoTests`: runner succeeded with no frontend tests because the scaffold has no meaningful interactive wallet behavior yet. This is not evidence of frontend behavior coverage.
- `pnpm exec tauri info`: configuration loaded and reported Tauri 2.11.6/API 2.11.1/CLI 2.11.5. After installing GTK, WebKit2GTK 4.1, librsvg and D-Bus development packages on the Fedora host, `cargo check -p ryo-wallet-next --locked` and a native `pnpm tauri dev` launch pass. A blank NVIDIA/WebKitGTK window was reproduced and the onboarding UI was visually verified with the documented DMABUF workaround. The default Wayland launch remained running without the earlier protocol error. Production packaging and capability-denial checks are still outstanding.
- `cargo clippy` is unavailable on the host's Fedora Rust installation. CI installs the pinned toolchain with clippy and attempts a native Linux Tauri check with development packages; neither job has run yet.

## Upstream compatibility finding

GitHub's latest core release is [0.6.1.0](https://github.com/ryo-currency/ryo-currency/releases/tag/0.6.1.0), published in 2020. Its source tag resolves to `166cf188bf351e3eecff904450eda2785f9d0357`. The 2026 inspected commit is `185dd1fa33ba88c88bb22df9069ad368c0f9a27e`. A Git diff found **no changes** between these commits in six RPC-relevant files: `wallet_rpc_server.cpp`, `wallet_rpc_server.h`, `wallet_rpc_server_commands_defs.h`, `wallet2.cpp`, `core_rpc_server.cpp`, and `core_rpc_server_commands_defs.h`. Registered methods and inspected wire shapes used by the current client therefore match at source level. The Linux 0.6.1.0 release archive was verified against its published SHA-256 and a valid signature from the upstream `mosu_forge` signing key (local trust is not asserted), then its wallet RPC binary was exercised only through disposable no-fund tests. In an isolated Fedora container, an out-of-tree source configuration required `-DCMAKE_POLICY_VERSION_MINIMUM=3.5` for CMake 4.3; after adding the missing build dependencies and a build-only `boost::asio::io_service` compatibility shim, compilation reached a second source-age incompatibility: `cryptonote_config.h` declares `boost::uuids::uuid` network IDs as `constexpr`, while Boost 1.90 no longer provides a constexpr constructor. The upstream clone remains unchanged. A supported historical dependency profile or an upstream-reviewed modernization is required before treating a source build as a runtime fixture.

Mock RPC and static source comparisons justify continued foundation work, not production compatibility. No mainnet funds are needed for these gates.
