# Security design

This is a threat model and release checklist, not a completed security audit. No wallet application has been implemented. Source evidence: [upstream analysis](UPSTREAM_ANALYSIS.md).

## Assets, adversaries and trust boundaries

Protect seed/private keys, wallet passwords, encrypted wallet files, spend authority, destination integrity, transaction metadata, node credentials and local privacy. Consider malicious remote nodes, network observers, browser content/XSS, crafted IPC and RPC responses, hostile import paths, malicious/replaced binaries and compromised dependencies. Same-user malware and a compromised OS can read input, manipulate the display or inspect processes; this desktop design cannot provide hardware-wallet isolation from them.

| Boundary / threat | Required control | Residual limitation |
| --- | --- | --- |
| Renderer → Rust | named commands, schema/bounds/session checks, least capabilities | an exploited authorized renderer may invoke allowed commands |
| Rust → wallet process | verified binary, authenticated loopback, bounded protocol | wallet-rpc holds live signing keys and exposes powerful RPC |
| Wallet → daemon | no wallet secrets, explicit node choice and trust | node learns timing/IP and can lie, censor or deny service |
| Hostile network | local mode preferred; explicit remote HTTP notice | inspected wallet CLI has no demonstrated verified TLS path |
| Disk/imports | owner-only dirs/ACLs, internal names, non-overwrite copies | backups and OS caches can retain older data |
| Dependency/update path | exact locks, provenance, review, binary hashes | a hash alone does not authenticate its publisher |

## Secret lifetimes

Passwords/seed input: keyboard → transient WebView input → one Tauri invocation → Rust zeroizing wrapper → authenticated local wallet-rpc request. Clear the input immediately after handoff and on errors/unmount/lock. Do not trim passwords. Normalize seed whitespace only in Rust. Use no secret-bearing generic Debug/Display/Serialize paths outside the necessary RPC/IPC serialization. HTTP body buffers and C++/WebView copies are not guaranteed to be zeroized; reducing lifetime is not a promise of perfect erasure.

Creation backup: upstream `query_key(mnemonic)` → Rust one-time backup response → dedicated UI → user writes recovery material. Do not query spend/view keys for this operation. After backup acknowledgement, clear seed and response buffers; require unlock again for later backup access. Seed must not enter event broadcasts, query caches, shared state, clipboard automatically, screenshots generated by tests, telemetry, logs or crash reports. Backup screens must warn about shoulder surfing without preventing accessible use. [src/wallet/wallet_rpc_server.cpp — `on_query_key`](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/src/wallet/wallet_rpc_server.cpp#L1273).

Spend/view keys stay in upstream wallet memory/files. Signed pending transaction metadata stays in Rust zeroizing memory and goes only to `relay_tx`; it is not harmless display data. Drop it on cancel, expiry, lock and node/session change. Non-secret submission journal hashes remain sensitive privacy metadata and receive owner-only access.

Wallet passwords are never written by Next to disk, argv, environment or settings. Ryo receives them through the local RPC payload and owns key encryption. Local RPC credentials are a distinct secret: wallet-rpc's generated-login file is an upstream feature in its private cwd. Read it safely and retain only for the lifetime required by the child; clear on exit and clean stale app-owned runtime directories. Do not describe this as passwordless RPC. [src/wallet/wallet_rpc_server.cpp — `init`](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/src/wallet/wallet_rpc_server.cpp#L198); [src/common/util.cpp — `private_file::create`](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/src/common/util.cpp#L93).

Managed daemon credentials, shared with wallet-rpc via daemon-login, may use generated owner-only temporary config files (no wallet password inside). Pass config path, not credentials, on argv; verify config parsing and access on all platforms before release. Avoid persistent node secrets in MVP. No user-authenticated public HTTP node credentials until transport confidentiality is supported; an advanced external tunnel must be explicitly selected and remain untrusted. Config-file support: [src/wallet/wallet_args.cpp — `main config handling`](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/src/wallet/wallet_args.cpp#L161); [src/daemon/main.cpp — `config loading`](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/src/daemon/main.cpp#L178).

## RPC and input hardening

- Bind owned wallet/daemon HTTP RPC to numeric 127.0.0.1; no external-bind flags, no CORS origins, no disable-rpc-login. Restrict/disable other listeners where supported; explicitly audit ZMQ and P2P separately.
- Use epee-compatible Digest challenge/response with fresh per-session credentials. Disable redirects and proxy environment inheritance; bound authentication retries and response bodies. HTTP authentication does not encrypt loopback payloads.
- Use app-owned endpoints only for wallet RPC. A frontend node endpoint may only affect a validated daemon connection, never the wallet RPC destination.
- No generic URL requests; restrict hostname/port syntax, schemes, length, redirects and intended destinations. Reject URL userinfo, fragments, embedded paths and shell metacharacters rather than building CLI strings. Remote endpoints must not accidentally target the wallet listener or unrelated local services.
- Revalidate decimal precision/overflow, wallet ID, account scope, restore height, payment ID and draft/session ownership in Rust. Keep backend validation authoritative. Unknown stale generation events cannot restore an old session.
- Managed filenames are generated IDs. Native selection yields a backend-owned import token; canonicalize and reject symlink/reparse-point traversal. Copy companions without overwriting, with a bounded file size policy; don't recursively import arbitrary directories.
- Never return raw RPC error bodies, request params, full paths or auth headers. Numeric upstream error codes and safe operation labels can be retained in diagnostics.

Source constraints: [src/rpc/rpc_args.cpp — `rpc_args::process`](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/src/rpc/rpc_args.cpp); [contrib/epee/include/net/http_auth.h](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/contrib/epee/include/net/http_auth.h); [src/wallet/wallet_rpc_server.cpp — `wallet_path_helper`](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/src/wallet/wallet_rpc_server.cpp#L2229).

## Tauri permissions and frontend surface

One local main WebView, remote origins disabled, no remote navigation, no arbitrary new windows. Capabilities must explicitly name this window and enumerate application operations. Do not grant frontend shell, filesystem, HTTP, process, generic updater-plugin or generic opener permissions. Update checking and installation are narrow Rust-owned commands with a fixed HTTPS feed and embedded public key. Native dialogs/clipboard writes are similarly scoped. Denied commands must be tested from a second/unprivileged WebView and a remote origin.

Register application commands in Tauri's application manifest/ACL build configuration and define explicit TOML permissions; merely writing a capabilities file must not be assumed to constrain every custom command. Test denial of each sensitive operation. Capabilities combine when they overlap, so avoid overlapping broad defaults. Tauri documents the [permission model](https://tauri.app/security/permissions/) and [capability merging](https://tauri.app/security/capabilities/).

Proposed production CSP, to validate on all three desktop engines with Tauri's generated nonces/hashes:

```text
default-src 'self'; script-src 'self'; style-src 'self';
img-src 'self' data:; font-src 'self';
connect-src ipc: http://ipc.localhost;
object-src 'none'; base-uri 'none'; frame-src 'none';
form-action 'none'; frame-ancestors 'none'
```

This is a design baseline, not a copied final configuration. Only Tauri transport origins required by the selected platform may be added after testing. No wallet RPC localhost URL is allowed in `connect-src`. Vite development allowances live only in dev configuration. Some shadcn primitives use inline styling: audit actual generated components, prefer class-based equivalents, and if a narrow `style-src-attr` exception is necessary document it; never relax script policy for convenience. Use [Tauri CSP support](https://tauri.app/security/csp/) and inspect the final packaged policy.

No remote JS/CDNs, HTML rendering of notes/errors, eval, third-party analytics, persisted WebView caches of wallet data or production devtools. Clipboard substitution remains possible; confirmation shows the full exact address from the Rust draft. Avoid automatic explorer opening and price/network widgets. Frontend dependencies and image/QR code renderers are part of the attack surface.

## Sidecars and platform ownership

Use Tauri `bundle.externalBin` for traceable packaging, with architecture-suffixed inputs. Rust process supervision owns launching and termination; no renderer shell API. Prefer `tokio::process::Command` behind an injected `BinaryLocator`, so services remain Tauri-independent. Resolve packaged paths using a tested platform adapter; never use PATH, the current directory or a user-writable random executable. [Tauri sidecar packaging](https://tauri.app/develop/sidecar/).

| Target | Initial architecture | Required checks |
| --- | --- | --- |
| Linux | x86_64-unknown-linux-gnu | execute bit, glibc/shared-library baseline, AppImage/deb/rpm paths, process-group shutdown |
| Windows | x86_64-pc-windows-msvc | .exe and DLL dependencies, owner ACL, no console window, Job Object cleanup, antivirus quarantine/missing binary |
| macOS | x86_64-apple-darwin | reviewed Intel core build, bundle resources, executable permission, eventual nested signing/notarization, child cleanup; Apple Silicon awaits a reviewable native runtime |

Target triples describe package targets; they do not prove upstream Ryo binaries currently exist for each. Separate macOS architecture packages are simpler initially than assuming a universal sidecar. Linux/Windows ARM64 and mobile are post-MVP pending upstream support.

Bundle both wallet-rpc and ryod in the eventual full desktop package, start ryod only in Local mode. During development, an explicitly configured external binary must still match an approved digest/build manifest before running. Missing/quarantined/wrong-architecture binaries yield clear failure, never unverified downloads or automatic node-mode changes.

Manifest per binary: upstream commit/tag, build recipe/toolchain, target, digest, license notices, expected version/protocol profile. Hash verification must anchor to reviewed signed release/build provenance, not a hash fetched beside an untrusted binary. Avoid executable replacement races by protected install locations and fail on modification. Running verified code as an unprivileged user does not sandbox that code from the user's wallet files.

App updates use Tauri's signed updater artifacts and require the signed version to match the release feed. Installation is requested only after a fresh version check and signature-verified download; the wallet service locks before replacement. Linux AppImage, Windows NSIS and macOS app bundles can self-update; DEB/RPM remain package-manager-owned. Production hardening still needs signing-key rotation and recovery planning, platform installation tests and rollback rules compatible with wallet-file formats. Disable upstream daemon autonomous update checks in managed launch using verified `--check-updates disabled`; upstream defaults to notify. [src/cryptonote_core/cryptonote_core.cpp — `arg_check_updates`](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/src/cryptonote_core/cryptonote_core.cpp#L117).

## Diagnostics, supply chain and release gates

Structured logs contain operation, duration, safe error code and random diagnostic ID, not seeds/passwords/auth/addresses/amounts/request bodies. Drain and cap child stdout/stderr without forwarding raw text to UI or normal logs. Ryo can log transaction metadata, so set the lowest practical tested log verbosity and treat any opt-in raw upstream log as private sensitive material. Avoid claiming that Rust redaction controls all C++ logs. [src/wallet/wallet2.cpp — `commit_tx logging`](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/src/wallet/wallet2.cpp#L4520).

Lockfiles for Cargo/pnpm; pinned build toolchains; review generated shadcn sources; restrict install scripts; audit dependency advisories and licenses; record an SBOM/build provenance before distribution. Pin CI actions to reviewed commits. PR CI has read-only permissions and no release secrets; never run untrusted PR code in a privileged workflow. Do not promise bit-for-bit reproducibility until independently reproduced across supported targets.

Release gates: authenticated loopback test; secret-canary log/cache tests; input/path/ACL negative tests; draft tamper/replay/session tests; crash and unknown-submission reconciliation; all supported binaries verified; platform process exit confirmed; licensing inventory completed. New remote transport support requires its own review and tests.
