### Address validation gap

`on_validate_address` exists, but `validate_address` is **absent** from the dispatch map. Its `any_net_type=false` branch also selects mainnet rather than the instance network. Calling it based on its declaration alone would fail. [src/wallet/wallet_rpc_server.cpp — `on_validate_address`](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/src/wallet/wallet_rpc_server.cpp#L2975); [src/wallet/wallet_rpc_server.h — `END_JSON_RPC_MAP`](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/src/wallet/wallet_rpc_server.h#L167).

MVP workaround: for an open wallet, Rust calls registered `parse_uri` with `ryo:` plus a bounded, syntactically clean address. `wallet2::parse_uri` calls `get_account_address_from_str(nettype(), ...)`, with no transaction side effect. Reject query delimiters in the plain-address field. `make_uri` can validate address + payment ID together, but its handler dereferences `m_wallet` without a null check; serialize against close and require an open session. Neither workaround reports a reliable address-kind/network classification. Return InvalidAddress unless a mismatch is actually established; never claim a prefix regex is full validation. [src/wallet/wallet_rpc_server.cpp — `on_parse_uri / on_make_uri`](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/src/wallet/wallet_rpc_server.cpp#L1997); [src/wallet/wallet2.cpp — `parse_uri / make_uri`](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/src/wallet/wallet2.cpp#L9150).

### Amounts, addresses and payment IDs

RYO uses **nine decimal places**, one RYO = 1,000,000,000 atomic units. Use Rust `u64` and checked arithmetic; serialize IPC amounts as decimal strings. [src/cryptonote_config.h — `CRYPTONOTE_DISPLAY_DECIMAL_POINT / MK_COINS`](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/src/cryptonote_config.h#L74).

The network-aware parser checks Base58 decoding, prefix, structure and public keys. It accepts current long addresses, legacy long addresses, integrated addresses, long subaddresses and Kurz addresses. Kurz subaddress parsing is deliberately commented out. This is richer than a textual `RYo` prefix test. [src/cryptonote_basic/cryptonote_basic_impl.cpp — `get_account_address_from_str<NETTYPE>`](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/src/cryptonote_basic/cryptonote_basic_impl.cpp#L324).

`wallet2::parse_payment_id` accepts 8- or 32-byte hex IDs (16 or 64 hex characters). `validate_transfer` rejects conflicting IDs and interprets integrated IDs; `make_integrated_address` uses an 8-byte ID. Preserve explicit payment IDs for users receiving exchange deposit instructions; do not silently drop them or invent Monero deprecation rules. [src/wallet/wallet2.cpp — `parse_payment_id`](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/src/wallet/wallet2.cpp#L3625); [src/wallet/wallet_rpc_server.cpp — `validate_transfer`](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/src/wallet/wallet_rpc_server.cpp#L587); [src/wallet/wallet_rpc_server.cpp — `on_make_integrated_address`](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/src/wallet/wallet_rpc_server.cpp#L1041). Actual recipient-service requirements need current confirmation; no exchange compatibility is claimed.

### Seed, files and lifecycle

Creation chooses long/Kurz account options, calls `generate_new`, and initializes scan height using daemon height and an estimate. Restore branches on 12/14 words versus 24/25/26 words, then invokes the upstream Electrum decoder: word count alone is not validation. When requested height is zero, restore may use a nonzero embedded seed restore height. Consequently zero does **not** always mean genesis scanning; full rescan is a separate option via `rescan_blockchain` with `full_rescan`. Normalize whitespace in Rust before submitting; never delete checksum words speculatively. [src/wallet/wallet_rpc_server.cpp — `on_create_wallet / on_restore_wallet`](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/src/wallet/wallet_rpc_server.cpp#L2255); [src/wallet/wallet_rpc_server.cpp — `on_rescan_blockchain`](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/src/wallet/wallet_rpc_server.cpp#L1319).

`start_wallet_backend` first calls `stop_wallet_backend`; stopping stores then deletes the old `wallet2`. `close_wallet` stores through that path; `stop_wallet` stores and requests server shutdown but fails when no wallet is open. Calling close then stop is therefore not a reliable shutdown sequence. [src/wallet/wallet_rpc_server.h — `start_wallet_backend / stop_wallet_backend`](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/src/wallet/wallet_rpc_server.h#L79); [src/wallet/wallet_rpc_server.cpp — `on_stop_wallet`](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/src/wallet/wallet_rpc_server.cpp#L1374).

`wallet2` owns key-file encryption, loading and cache storage. `prepare_file_names` delegates naming to `do_prepare_file_names`; `.keys` accompanies the wallet cache; `.address.txt` and Atom `.meta.json` are ancillary. Preserve imported originals, operate on an app-owned copy and never treat a cache alone as the backup. Encryption implementation is retained upstream, not reproduced here. [src/wallet/wallet2.cpp — `store_keys / load / prepare_file_names`](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/src/wallet/wallet2.cpp#L2400); [src/wallet/wallet2.cpp — `prepare_file_names`](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/src/wallet/wallet2.cpp#L3653); [src-electron/main-process/modules/wallet-rpc.js — `listWallets / importWallet`](https://github.com/ryo-currency/ryo-wallet/blob/6c8d0aa68245271fe0e781084b38583abf758869/src-electron/main-process/modules/wallet-rpc.js).

`wallet_path_helper` rejects selected punctuation and `..`, but does not provide our desired canonical-path containment and symlink defense. The service must generate safe internal filenames independently. [src/wallet/wallet_rpc_server.cpp — `wallet_path_helper`](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/src/wallet/wallet_rpc_server.cpp#L2229).

### Signing, broadcasting and uncertainty

`on_transfer_split` constructs a vector of pending transactions through `create_transactions_2`. `fill_response` skips `commit_tx` when `do_not_relay` is true, returning hashes, amounts, fees and requested metadata. Construction already reaches signing (`construct_tx_and_get_tx_key`, `genRctSimple`/`genRct`). The viable UX is **prepare/sign locally → review actual fee → explicitly relay**. It is not deferred signing after confirmation. [src/wallet/wallet_rpc_server.cpp — `on_transfer_split / fill_response`](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/src/wallet/wallet_rpc_server.cpp#L693); [src/wallet/wallet2.cpp — `create_transactions_2`](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/src/wallet/wallet2.cpp#L6446); [src/cryptonote_core/cryptonote_tx_utils.cpp — `construct_tx_and_get_tx_key / genRctSimple`](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/src/cryptonote_core/cryptonote_tx_utils.cpp#L542).

`on_relay_tx` decodes its hex field as a portable-binary `pending_tx`, calls `commit_tx`, and returns a hash. Keep this opaque sensitive metadata exclusively in Rust. `commit_tx` sends `/sendrawtransaction` before recording the local unconfirmed transaction and spent outputs. A transport failure can leave the submission outcome unknown; multiple split transactions can partially succeed. Do not regenerate or blindly retry a payment. [src/wallet/wallet_rpc_server.cpp — `on_relay_tx`](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/src/wallet/wallet_rpc_server.cpp#L996); [src/wallet/wallet2.cpp — `commit_tx`](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/src/wallet/wallet2.cpp#L4481).

### Synchronization and errors

`wallet_rpc_server::run` refreshes in an idle handler every 20 seconds and runs a single RPC server thread, explicitly warning against increasing the thread count. Long refresh can delay unrelated RPC commands. `get_height` reports wallet height, not a complete freshness guarantee. [src/wallet/wallet_rpc_server.cpp — `run`](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/src/wallet/wallet_rpc_server.cpp#L115); [src/wallet/wallet_rpc_server.cpp — `on_getheight`](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/src/wallet/wallet_rpc_server.cpp#L573).

History has height filters and account/subaddress filters, no native cursor/offset pagination. The service builds bounded snapshots/cursors and merges pending/pool state; large histories require range queries and response limits. [src/wallet/wallet_rpc_server_commands_defs.h — `COMMAND_RPC_GET_TRANSFERS`](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/src/wallet/wallet_rpc_server_commands_defs.h#L1219); [src/wallet/wallet_rpc_server.cpp — `on_get_transfers`](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/src/wallet/wallet_rpc_server.cpp).

Numeric error definitions and exception mapping cover wrong address (-2), not-open (-13), insufficient total/unlocked funds (-17/-37), existing wallet (-21), invalid password (-22), and daemon connection (-38). Many failures still collapse to -1 or -4. `on_relay_tx` loses detailed commit exceptions. Never map every generic transfer error to definite rejection. [src/wallet/wallet_rpc_server_error_codes.h](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/src/wallet/wallet_rpc_server_error_codes.h); [src/wallet/wallet_rpc_server.cpp — `handle_rpc_exception`](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/src/wallet/wallet_rpc_server.cpp#L2520); [src/wallet/wallet_rpc_server.cpp — `on_relay_tx`](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/src/wallet/wallet_rpc_server.cpp#L996).

## Daemon RPC, network and authentication

`core_rpc_server` provides a mixture of `/json_rpc` methods (`get_info`, `get_version`, block headers) and HTTP JSON endpoints (`/getheight`, `/sendrawtransaction`, `/stop_daemon`), plus binary synchronization endpoints. Rust only needs typed health/version/header calls and lifecycle control; wallet-rpc handles chain scanning and transaction protocol. [src/rpc/core_rpc_server.h — `URI and JSON-RPC maps`](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/src/rpc/core_rpc_server.h#L94).

| Network | P2P | daemon HTTP RPC | ZMQ |
| --- | --- | --- | --- |
| Mainnet | 12210 | 12211 | 12212 |
| Testnet | 13310 | 13311 | 13312 |
| Stagenet | 14410 | 14411 | 14412 |

These are `config<MAINNET/TESTNET/STAGENET>` constants, not wallet-rpc ports. Allocate a separate wallet-rpc port per managed instance; never infer it from daemon defaults. `network_type` also has FAKECHAIN and UNDEFINED; FAKECHAIN alone does not prove a turnkey private-network test harness. [src/cryptonote_config.h — `network_type / config specializations`](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/src/cryptonote_config.h#L156).

`get_info` includes `height`, `target_height`, `mainnet`, `testnet`, `stagenet`, `is_ready`, `offline`, bootstrap and `untrusted` fields. Treat remote values as claims. A local readiness claim, recent top block and wallet scan height together form a conservative service sync state; define/test off-by-one semantics before unlocking Send. [src/rpc/core_rpc_server_commands_defs.h — `COMMAND_RPC_GET_INFO`](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/src/rpc/core_rpc_server_commands_defs.h#L940); [src/rpc/core_rpc_server.cpp — `on_get_info / on_get_info_json`](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/src/rpc/core_rpc_server.cpp).

RPC bind defaults to 127.0.0.1; external bind requires confirmation. RPC login is supported, CORS is configurable, and epee implements RFC 2617 Digest authentication. Wallet RPC generates credentials into `ryo-wallet-rpc.<port>.login` in its working directory if login is omitted; disabling login is optional upstream and forbidden in Next. A private runtime working directory is therefore useful. Windows private files use owner ACL/delete-on-close; Unix uses owner-access handling. Verify both from a running parent process before adopting generated-login mode. [src/rpc/rpc_args.cpp — `rpc_args::descriptors / process`](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/src/rpc/rpc_args.cpp#L62); [src/wallet/wallet_rpc_server.cpp — `init`](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/src/wallet/wallet_rpc_server.cpp#L149); [contrib/epee/include/net/http_auth.h](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/contrib/epee/include/net/http_auth.h); [src/common/util.cpp — `private_file::create / destructor`](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/src/common/util.cpp#L93).

Wallet daemon credentials use `--daemon-login`. In the inspected CLI construction path, `wallet->init(address, login)` uses default `ssl=false`, and the HTTP client stores that flag separately from the URL. Merely typing `https://` does not establish verified TLS support. A comment in `net_helper.h` says certificate verification is disabled, while the code sets `verify_peer`: neither proves hostname verification or a usable CLI TLS path. Next must reject direct HTTPS in this compatibility profile until tested; it must never silently downgrade. [src/wallet/wallet2.cpp — `make_basic / wallet->init`](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/src/wallet/wallet2.cpp#L256); [src/wallet/wallet2.h — `init`](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/src/wallet/wallet2.h#L616); [contrib/epee/include/net/http_client.h — `set_server`](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/contrib/epee/include/net/http_client.h#L281); [contrib/epee/include/net/net_helper.h — `connect`](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/contrib/epee/include/net/net_helper.h#L163).

Local daemon addresses are automatically considered trusted if `trusted-daemon` is not explicitly supplied. Explicitly configure and test false for remote mode, including a local SSH/TLS tunnel to a remote daemon. Do not equate loopback transport with ownership of the remote node. [src/wallet/wallet_rpc_server.cpp — `init`](https://github.com/ryo-currency/ryo-currency/blob/185dd1fa33ba88c88bb22df9069ad368c0f9a27e/src/wallet/wallet_rpc_server.cpp#L177).

## Licensing

Their `ORIGINAL-LICENSE` files preserve BSD-3 conditions for inherited portions and explicitly distinguish Ryo modifications. These texts are not a simple blanket MIT/BSD permission. The dates have passed, but scope, later contributions, file headers, assets, submodules and jurisdictional effect still need review before redistribution. This is an inventory finding, not a legal conclusion about enforceability.

## Questions for Ryo developers and release gates

1. Which maintained core commit/release is the supported wallet baseline, and which signed/hash-verified binary artifacts correspond to it on each target?
2. Is missing `validate_address` registration intentional? Can the correct network-aware method be supported in a future upstream release?
3. What is the supported verified-TLS daemon connection path for wallet-rpc, including hostname checking and credentials?
4. Is explicit `--trusted-daemon=false` supported consistently for tunneled remote nodes in released binaries?
5. Are detached prepared metadata, cancellation/output selection and partial relay semantics stable across supported versions? What recovery is recommended after broadcast succeeds but local bookkeeping fails?
6. Which seed/Kurz/legacy formats must be covered, and how should users override an incorrect embedded restore height?
7. Is there a maintained isolated testnet/fixture recipe, with enough mature outputs/ring members for repeatable transfers? Are public testnet/stagenet active?
8. Which wallet-file versions can safely be imported, and what downgrade/cache migration limits apply?
9. Can licensing intent for current files, later contributions, redistributed binaries and branding be clarified in writing?
10. Are Linux ARM64, Windows ARM64 and macOS Apple Silicon core binaries supported? What operational scan/shutdown limits are expected for large wallets?

These questions do not block drafting or RPC mocks. Binary compatibility, authenticated process startup, uncertain transfer recovery and platform packaging are release gates.
